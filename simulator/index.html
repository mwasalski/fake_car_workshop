README

Co to jest

Lokalny symulator ERP platformy fake_car_workshop: generuje dokładnie ten sam syntetyczny zbiór danych, co notebooki na Databricks, ale bez Sparka i bez chmury. Logika generacji jest współdzielona — moduły simulator/dims_generation.py i simulator/fact_generation.py importują zarówno notebooki (initial_dims.ipynb, daily.ipynb), jak i ta aplikacja. Jedna implementacja, dwa środowiska.

Szybki start

  1. 1 · Dimensions — jednorazowo. Buduje 7 tabel wymiarów (seed 42): lokalizacje, pracownicy, klienci, pojazdy, produkty, usługi, dostawcy.
  2. 2 · One day of facts — jeden dzień danych z 13 tabel faktów (sprzedaż, zlecenia warsztatowe, faktury, płatności, magazyn…). Puste pole daty = wczoraj.
  3. 3 · Backfill — pętla po zakresie dat (max rok na żądanie); lokalny odpowiednik backfill.ipynb.
  4. Preview — podgląd pierwszych N wierszy (do 10 000) dowolnej wygenerowanej tabeli.

Parametr scale

  • Fakty: scale=1.0 ≈ 100 000 wierszy/dzień; 0.05 = 5% tej objętości. Dla tej samej trójki (data, scale, dimy) wynik jest identyczny przy każdym uruchomieniu (seed = data).
  • Wymiary: scale < 1.0 to wygoda do lokalnych testów — zmniejsza klientów/pojazdy/dostawców, ale zmienia konsumpcję RNG, więc wiersze różnią się od pełnego zbioru z Databricks. Pełna zgodność: scale=1.0.

Determinizm i bloki ID

RNG jest zasiewany datą (seed = YYYYMMDD), a każdy dzień dostaje rozłączny blok 10 mln ID na tabelę (ID_START = dni_od_2020-01-01 × 10M) — ID nigdy nie kolidują między dniami. Ponowne wygenerowanie tej samej daty tworzy identyczne wiersze, ale nowe pliki (duplikaty są celowym materiałem do ćwiczeń z deduplikacji w silver). Klauzula: fact_payments.transaction_number używa uuid4 i jako jedyna kolumna łamie determinizm (znany dług, śledzony w journalu).

Semantyka danych (skróty)

  • customer_id = NULL w sprzedaży = klient bez rejestracji (~30%, celowy skew).
  • work_order_items: sentinel 0 w nieużywanym FK usługa/produkt.
  • Daty w parquetach to prawdziwe date32 (nie timestampy) — kontrakt z tabelami Delta.

Układ danych na dysku

data/ dim_landing/<tabela_dim>/snapshot.parquet fact_files/<tabela_fact>/[year=…/month=…/]*.parquet

W kontenerze to volume /data; lokalnie katalog ./data (w .gitignore). Układ odzwierciedla volumeny na Databricks.

API

GET /api/status wygenerowane tabele + liczby wierszy POST /api/generate/dims?scale= 7 wymiarów (seed 42) POST /api/generate/day?day=&scale= 1 dzień, 13 tabel faktów POST /api/generate/backfill?start=&end=&scale= zakres dat GET /api/preview/{tabela}?n= pierwsze n wierszy jako JSON

What this is

The local ERP simulator of the fake_car_workshop platform: it generates exactly the same synthetic dataset as the Databricks notebooks, but with no Spark and no cloud. The generation logic is shared — modules simulator/dims_generation.py and simulator/fact_generation.py are imported both by the notebooks (initial_dims.ipynb, daily.ipynb) and by this app. One implementation, two environments.

Quick start

  1. 1 · Dimensions — one-time. Builds the 7 dimension tables (seed 42): locations, employees, customers, vehicles, products, services, suppliers.
  2. 2 · One day of facts — a single day across 13 fact tables (sales, work orders, invoices, payments, inventory…). Blank date = yesterday.
  3. 3 · Backfill — loops over a date range (max one year per request); the local equivalent of backfill.ipynb.
  4. Preview — first N rows (up to 10,000) of any generated table.

The scale parameter

  • Facts: scale=1.0 ≈ 100,000 rows/day; 0.05 = 5% of that. For a given (date, scale, dims) triple the output is identical on every run (seed = date).
  • Dimensions: scale < 1.0 is a local-testing convenience — it shrinks customers/vehicles/suppliers but changes RNG consumption, so rows differ from the full Databricks dataset. Full parity: scale=1.0.

Determinism & ID blocks

The RNG is seeded with the date (seed = YYYYMMDD) and every day owns a disjoint 10M ID block per table (ID_START = days_since_2020-01-01 × 10M) — IDs never collide across days. Re-generating the same date produces identical rows but new files (the duplicates are deliberate exercise material for silver-layer dedup). Caveat: fact_payments.transaction_number uses uuid4 and is the one column that breaks determinism (known debt, tracked in the journal).

Data semantics (highlights)

  • customer_id = NULL in sales = walk-in customer (~30%, deliberate skew).
  • work_order_items: sentinel 0 in the unused service/product FK.
  • Dates land in parquet as real date32 (not timestamps) — the Delta-table contract.

Data layout on disk

data/ dim_landing/<dim_table>/snapshot.parquet fact_files/<fact_table>/[year=…/month=…/]*.parquet

Inside the container this is the /data volume; locally it is ./data (git-ignored). The layout mirrors the Databricks volumes.

API

GET /api/status generated tables + row counts POST /api/generate/dims?scale= 7 dimensions (seed 42) POST /api/generate/day?day=&scale= one day, 13 fact tables POST /api/generate/backfill?start=&end=&scale= a range of days GET /api/preview/{table}?n= first n rows as JSON
